# 内部设计

本文档面向修改代码的开发者，说明模块分工、提示词的组装方式，以及记忆和接话机制。使用方法见 [README](../README.md) 和 `docs/` 里的其他文档：[写角色包](characters.md)、[配置](configuration.md)、[聊天](chat.md)、[接入聊天软件](gateway.md)、[连接器协议](protocol.md)。

ohMyRhine 让 LLM 稳定地扮演一个角色，支持群聊、多人记忆、知识边界控制。平台连接由外部连接器通过[连接器协议](protocol.md)接入，不在本项目范围内。

---

## 1. 总体结构

```
[聊天软件] ⇄ 外部连接器 ⇄ gateway（WebSocket，防抖、限流、把会话交给对应角色）
                               │
   rhine chat / rhine web ⇄  engine：收消息 → 接话判定 → 组装上下文 → 生成 → 存储
                               │
                         store（每个角色一个 SQLite：编译后的角色包、消息、记忆、情景、媒体）
                               ▲
                         pack（角色包：作者编写的纯文本，git 管理，自动编译）
```

| 模块 | 职责 |
|---|---|
| `pack/` | 角色包格式、校验、编译 |
| `store/` | SQLite 存储 |
| `engine/` | 运行时：`engine.py` 主流程，`prompt.py` system prompt 与对话记录，`judge.py` 群聊筛选，`memory.py` 长期记忆，`media.py` 图片，`context.py` 上下文统计 |
| `catalog.py` | 第一层配置：内置的供应商、模型（能力和价格）、任务和查资料用的 agent。`config.py` 是第二层，把 `config.yaml` 解析成每个任务的 `ModelSettings` |
| `providers/` | LLM 适配：Anthropic、OpenAI 兼容、echo（测试） |
| `gateway/` | 连接器协议与服务端 |
| `local.py` | 本机的对话（`rhine chat` 和 `rhine web` 共用）：会话、多角色、引用、撤回、拍一拍，产出事件给界面显示 |
| `chat_repl.py`、`web/`、`cli.py` | 终端界面、网页界面（HTTP 和 WebSocket 同一个端口）、命令行 |
| `evals.py` | 评测场景的读取和运行（`rhine eval`） |
| `plugins.py` | 项目之外的代码接进来的地方 |

## 2. 角色的知识结构

| 层 | 内容 | 来源 | 可变性 |
|---|---|---|---|
| ① 核心人设 | 身份、性格、内核、说话方式、示例对话 | 作者 | 只读，每轮都在 prompt 中 |
| ② 设定 | 背景经历、世界观、设定内人际关系、秘密 | 作者 | 只读 |
| ③ 习得记忆 | 认识的人、聊过的事、关系变化 | 运行时 | 增长、改写 |
| ④ 知识边界 | 知道 / 不知道 / 知道但不说 / 世界外知识策略 | 作者 | 只读（规则） |

**原则：设定是事实，习得记忆是经历。** 冲突时设定优先；关于角色自身的新事实只有作者能写入。

### 2.1 世界真相 vs 角色认知

世界观条目区分 `truth`（世界真相）和 `known_by`（某角色所知的版本）。给模型的永远是**角色所知版本**；模型没看到的内容就无从泄露。

### 2.2 知识状态

| 状态 | 实现 |
|---|---|
| 知道，会说 | 进入 prompt |
| 知道，不愿谈（秘密） | `secrets.yaml`：只把应对方式（`when_hidden`）放入 prompt，内容本身不放入。`reveal_when` 为预留字段，暂不生效 |
| 经历过，但想不起来（封存的记忆） | `sealed.yaml`：内容和会触及它的事物（`echo`，只写触发物，不写预设的感受）都进入 prompt，放在单独的「封存的记忆」部分。规则要求不说出其中任何内容；触及时的感受由模型根据那段经历对角色的意义推断。多数情况下只表现为反应与平时略有不同，角色不点破；需要解释时以眼前的事为由，即使说出口也使用角色自己的话。由于模型知道真相，存在泄露风险，需用评测场景检查是否泄露 |
| 不知道（世界内） | 不进入 prompt；通用规则要求不编造设定之外的经历和线索 |
| 世界外知识 | `knowledge_domains` + `out_of_world_policy` + 说话示例 |

## 3. 角色包

格式和写法见[写角色包](characters.md)。`pack/loader.py` 读角色包、按 `known_by` 过滤世界观、去掉秘密的内容，编译成 `CompiledPack` 存进角色的数据库。

- 人称约定：角色包和引擎的提示词中，角色的经历、感受和处境使用角色名或代词；「你」只指扮演者，即模型本身。引擎的通用提示词用角色包的 `pronoun` 称呼角色。
- 角色包和编译器（`pack/loader.py`、`pack/schema.py`）的内容一起算哈希。两者有任何变化，下次运行时自动重新编译，重新编译不影响习得记忆。

## 4. Prompt 结构

遵循 Anthropic 提示词建议：

- system prompt 按「角色资料（XML 标签分区）→ 说话示例 → 角色专属规则 → 扮演方式说明」排列，资料在前、行为说明在后、离对话最近。
- 说明用带理由的段落而非条目。prompt 本身不用 markdown，避免引导输出 markdown。
- system prompt 不含任何逐轮变化的内容，整体可缓存。

每次请求由四部分组成，越靠后变化越频繁：

1. 可缓存的人设（system 第一段）。同一角色的所有会话共用这一段，因此回复请求为其设置一小时的缓存（写入价格为输入的 2 倍，每次命中续期）：群聊沉寂 5 到 60 分钟后再次回复时，只需重写对话记录，无需重写人设。对话记录和各小任务仍使用 5 分钟缓存。
2. 这个会话的情景、窗口之前的系统指令、更早聊天的摘要，和窗口开头那一刻角色已有的笔记（system 第二段，在人设的缓存断点之后）。后三者只在历史窗口裁剪时变化，而裁剪本身就会使历史缓存失效。
3. 对话记录（messages）。每条消息是单独的一个内容块，缓存断点打在最后一块上，并在它之前每隔 15 块再打一个（一共 3 个，人设占第 4 个）。原因：一次请求只能命中之前某次请求设置过断点的位置，且每个断点最多向前查找 20 块。角色在群里不回复时，待回答的这一段持续变长；若整段为一个块，上一次的断点落在块的中间，下一次无法命中，每次都要把整段历史重写进缓存。分块之后，上一次请求的每一块都原样成为下一次的前缀，相隔几十条消息也能命中。OpenAI 兼容接口仍把一段拼成一个字符串，这些服务按字节前缀缓存，不受影响。他人的每条消息包在 `<msg from=… id=…>` 里，引用、图片、机器人和系统标记都放在标签和属性中。正文、昵称、引文和记忆里的尖括号会转成全角，因此用户输入的文字无法冒充系统标注。时间由消息的 `time` 属性和长间隔处的 `<gap>` 给出：每段新消息的第一条以及长间隔后的第一条写完整的日期和时刻，同一段中其后的消息只写变化的部分（跨日写完整时间，跨分钟只写时刻，同一分钟不写）。一条消息的写法只取决于其前一条，因此后来的消息不会改动已发送的内容，历史缓存不受影响；待回答的一段总是以完整的日期和时刻开头。摘要读取的记录仍然每条都带完整时间。
4. 每轮都可能变化的少量内容，附在最后一条消息之后、缓存断点之后：笔记过长时提醒角色整理（`<notes_reminder>`），以及分条发送的回复中未发出的部分（`<unsent>`）。

**控制上下文长度**：

- **超长消息**：超过 1600 字的普通聊天消息只显示开头 800 字，其后附一份由 `summary` 任务生成、800 字以内的摘要（`<digest>`）。摘要在该消息首次交给模型之前生成，此后显示内容不再变化。系统指令保留全文。
- **读原文**：角色拥有 `read_message` 工具，需要细节时可按段读取原文，每段 800 字。已撤回的消息无法通过工具读取。读取过程只存在于当次回复中，不写入记录，因此不影响缓存；Anthropic 和 OpenAI 兼容接口均支持，每次回复的工具调用合计最多 4 次。
- **翻阅以前的记录**：窗口之前的原文由查资料的 agent 翻阅（`agent_history`，见 §7「查资料」）。
- **其他上限**：历史按 token 预算；引用只截取前 60 字；每轮最多附 4 张原图。

**历史窗口和自动压缩**：按估算的 token 计（汉字约 1 个、其他字符约 0.6 个），预算 `history_tokens`（默认 24000）。
- 自动压缩（`Engine.compact`）：网关每次处理完新消息后在后台检查，窗口超过预算的六分之五（20000）时压缩：保留最新的、至少占预算四分之一（6000）的消息，更早的交给滚动摘要。回复不等待压缩。
- 请求时窗口已超过整个预算（例如在 CLI 中，或短时间内涌入大量消息）时，该请求按同样的规则自行裁剪。
- 两次压缩之间窗口起点（`window_from`）不变，因此历史前缀能持续命中缓存。窗口不会以角色自己的发言开头。
- 摘要在后台生成（需要数秒），回复从不等待摘要；摘要尚未完成时，相应消息暂留在窗口中（最多多保留一个预算），因此不会遗漏，裁剪和替换新摘要发生在同一次请求中，缓存只失效一次。
- 被压缩的部分，角色可以通过查资料的 agent 翻阅原文（`agent_history`）。

## 5. 记忆与情景

**长期记忆**（`engine/memory.py`）：

- **由角色记录**：回复时角色用三个工具管理自己的笔记：`add_memory` 记录一条（可注明关于谁），`edit_memory` 改写一条，`remove_memory` 删除一条（需写明原因）。
  - 工具说明规定了记录范围：必须记录角色答应他人的事（即使只回了一句「嗯」）、他人要求角色今后如何做（称呼、说话方式）；值得记录的是在场者自己的事、群里约定的事；寒暄、聊天经过、真实的住址电话、他人关于角色过去的说法都不记录。
  - 只删除记错的或明确作废的笔记；已完成或已过去的事改写为后续结果。
- **先发送再记录**：工具说明要求角色先写完回复再记笔记。角色写出回复后开始调用记笔记的工具时，回复即视为完成（`ReplyWritten`）：网关立即发出回复，笔记在后台继续写完，本次回复到此结束，不再为让角色查看工具结果而多发一次请求。角色也可以先记笔记再回复，代价是多一次请求。Anthropic 和 OpenAI 兼容接口均支持。
  - 回复未发出（有人插话需要重写、读过的系统指令被撤销、连接器离线）时，其笔记不予记录：笔记工具执行前先检查该回复是否仍然存在。
  - 同一会话的下一次回复等待上一次的笔记写完，因此能看到这些笔记。
- **注入**：每次回复都附带该会话的全部笔记，不按在场者筛选，也不限条数。笔记的改动只向后追加，历史缓存始终有效：
  - 对话记录之前（system 第二段，摘要之后）是历史窗口起点时已有的笔记（`<long_term_memory>` 中的 `<note id about person written>`）。`written` 为记录或最后修改的日期，按角色的时区写具体日期；没有时钟的角色不写。
  - 此后每次记录、改写、删除、恢复，都在对话记录中相应的位置出现一行（`<note change="add|edit|remove|restore">`，改写附改后的全文，删除的正文为原因）。位置由改动时库中最新的消息（`memory_changes.after_id`）决定：排在该消息之后、更新的消息之前，因此新的一行只会接在已发送的内容之后。紧跟在角色最后一条回复之后的改动，等下一条消息到达时再一并出现，否则它会单独成为需要回答的一轮。
  - 窗口裁剪时，前面的笔记按裁剪后窗口的起点重新计算（将之后的改动倒推回去），窗口中的改动行随之消失。这与替换新摘要发生在同一次请求中，缓存只失效一次。
  - 笔记随历史前缀一起缓存，缓存过期或窗口裁剪时才需重写。
  - 总长超过 `memory.notes_chars`（默认 4000 字）时，在末尾附一句提醒，要求角色合并描述同一件事的笔记、删除已失效的笔记，但全部笔记仍照常附带。
- **不会自动丢失**：只有角色本身和主人（通过命令行）能修改笔记。
  - 每次记录、改写、删除、恢复都写入 `memory_changes` 表：操作者、时间、修改前的内容、删除原因，以及当时库中最新的消息（`after_id`，第 9 版加入；更早的改动按时间补齐）。
  - 删除的笔记保留在库中，可用 `rhine memory restore` 恢复；`rhine memory rm --purge` 连同记录彻底删除，用于不应留存的内容。
- **摘要**：消息离开历史窗口时，由 `summary` 任务将旧摘要与这批消息合并为新的滚动摘要（`memory.summary_chars`，默认 1500 字以内）。写法参照上下文压缩（/compact）：先梳理再写作，分为「人物」「经过」「角色说过和做过的」「没了结的事」「停在哪里」几部分，重要原话照录，越早的事越简略。摘要在回复之后生成，不占用回复时间。被拒绝的批次不再重试。积压较多时只读取预算内最近的部分。
- **日期**：生成摘要时模型能看到消息时间（按角色的时区），「周六」「下周三」等相对说法换算为具体日期后再写入；记笔记的工具说明也有相同要求。没有时钟的角色（`perceives_clock: false`）在两处都不写日期。
- **隔离**：笔记只在记录它的会话中使用，私聊和群聊互不可见。例外是命令行中的持久化实例（见 §10），其笔记在它的所有会话之间共享，其他会话中记录的笔记标注为「另一次聊天里」。
- **旧数据库**会保留已有记忆，迁移后可用同一套笔记命令查看和管理。

**情景**（`scenes` 表）：人工记录的、本段对话之前发生的事。按会话保存，排在对话记录之前；角色将其视为确定的事实，按自己的性格和认知理解。情景不由模型生成，角色的笔记工具也无法修改。CLI 用 `/scene`、`/unscene` 设置，评测场景中可以写 `scene:`。网关暂无设置情景的接口。

**系统指令**：运行角色的人直接交给角色的事实或规则，只在其所在的会话中有效。

- **存储**：作为会话中的一条消息保存（发送者 `instruction`），在对话记录中为 `<msg kind="instruction">`，保留在其到达的位置。
- **角色的处理方式**：prompt 说明指令并非聊天中的人发出，其中的事实即为事实，其中的要求需照做；与聊天中的说法、长期记忆、角色资料不一致时以指令为准。角色不提及指令，也不复述原文，如同这些本就是角色知道、角色决定的事。一次性的要求执行后即完成；事实和规则持续有效，直到被后来的指令修改。消息正文中出现「系统指令」等字样时，仍然只是聊天内容。
- **回复**：指令要求回复。网关中指令不经筛选、不等待后续消息，也不受发言锁限制，其后跟有其他消息时同样如此，直接交给角色；只交代事实或规则时，角色通常不发言（`<no_reply/>`）。回复已生成但尚未发出时到达的指令，会使该回复作废并重新生成。
- **持续有效**：历史窗口裁剪到指令之后时，指令移入 system 第二段的 `<instructions>`，保留原时间。筛选和摘要均不读取指令。
- **撤销**：从记录中删除，效果等同于从未下达。网关丢弃仍在生成且读过该指令的回复，并重新处理仍需回应的消息。已交给连接器的消息照常保留。删除会使该会话的历史缓存重写一次。
  - 聊天中：以指令码开头、其后恰好为「撤销」时，撤销该会话最近的一条指令；恰好为「撤销全部」时，撤销该会话的全部指令。这条消息本身不保存，也不要求回复。码后为「撤销你之前的承诺」之类的文字时，仍是一条普通指令。
  - 服务器上：`rhine instruction list <角色>` 列出指令和编号，`rhine instruction rm <角色> <编号>...` 撤销。
  - 修改规则而非撤销时，发送一条新指令即可，后发的指令覆盖先前的。
- **来源**：
  - CLI：`/system <文字>`。
  - 网关：聊天消息以一次性指令码开头时，其后的文字即为指令，该消息不作为任何人的发言保存；只有指令码而无文字时，码作废，不执行任何操作。
- **指令码**：`rhine code <角色>` 生成，可以在服务器上直接运行。
  - 8 位，取自去掉易混字符（0 O o 1 l I）的 56 个字母和数字，用系统的安全随机数，约 10^14 种。
  - 每个角色同一时间只有一个码，生成新码时旧码作废。默认 10 分钟内有效（`--minutes`），使用一次即作废；网关和命令行同时运行时也只能使用一次。
  - 数据库里只存它的哈希，比较用常数时间。
  - 码发在群里后，群成员能看到这条消息，但此时码已作废。

## 6. LLM 路由

按**任务**配置模型，任务和配置写法见[配置](configuration.md)。配置分两层：代码里的内置表（`catalog.py`），和 `config.yaml` 里对它的选择和覆盖（`config.py`）。加载时逐项解析成每个任务的 `ModelSettings`，无法满足的配置在启动时报错。新增供应商、模型或 agent 时在 `catalog.py` 中添加一项；新增协议时还需在 `providers/` 中编写适配器。

OpenAI 兼容服务返回 400 或 422 且错误信息指明请求的某一部分时，适配器修改该部分后重试：结构化输出 `json_schema` → `json_object` → 只在提示词里写明格式；输出上限改用另一个字段名；去掉 `reasoning_effort`；去掉 `stream_options`。修改在进程运行期间持续沿用，并记录一条警告。

未配置的小任务，其对应功能不启用。小任务的对话内容每次都不同，因此只缓存 system，不在对话上设置缓存断点（写入缓存比普通输入更贵）。

角色回复使用流式接口。默认连续 60 秒没有收到数据会触发读取超时（`stream_timeout_s`），尚未收到响应时 SDK 最多重试两次。小任务使用各自 SDK 的默认超时。

## 7. 接话与回复

- **身份**：一律使用带平台前缀的稳定 ID，昵称可以变化。
- **必定回复**：私聊；被 @；引用了角色的消息；系统指令（见 §5）；未配置筛选时，提到角色名字也包括在内。
- **筛选**（`reply_judge`）：只做一道快速、低成本的筛选，是否回复以及如何回复由角色自己决定。
  - 只参考角色的名字、擅长和喜欢的事，以及最近 `group.judge_context`（默认 12）条消息。
  - 是否交给角色：判断角色看到这批消息后是否会开口。有人在对角色说话（叫名字、向角色提问、提到角色、谈论角色的事、接着角色的话说下去，即使只是附和一句）时交给角色；谈论角色本人时，即使是对他人说的也交给角色；他人之间谈论其他事情时，即使话题是角色擅长或喜欢的，也不交给角色。无法确定是否有人在对角色说话时，交给角色。未交给角色的消息视为已处理。
  - 筛选放行后，角色仍可用 `<no_reply/>` 保持沉默。这次生成也会产生用量，因此筛选应尽量接近角色自己的接话判断。
  - 等待时间（`wait`）：筛选另外判断最新一条消息的发送者是否已说完。已说完时不等待；看得出正在分条发送时，短暂等待（`short`，默认 6 秒）；话说到一半时，等待更久（`long`，默认 15 秒）。等待期间消息暂存，有新消息到达时一并重新判断；等待结束仍无后续消息时，按原先是否交给角色的结论处理。
  - 群里必定回复的消息（被 @、引用了角色的消息）同样先经过筛选，但只采用其 `wait`，必定交给角色。发言锁除外（见下）。
  - 两档等待时间可用 `group.wait_short_s` 和 `group.wait_long_s` 调整。
- **发言锁**：筛选发现新消息中有人不希望角色此时发言（要求角色先别说话、闭嘴、别插嘴）时，为该群加锁（`hush`，记录在 `chats.hushed`，重启后保留）。
  - 触发加锁的这批消息不交给角色，即使其中有 @ 角色的消息。
  - 加锁期间，新消息只作为上下文，不经过筛选；引用角色的消息也不回复。系统指令不受影响。
  - 有人 @ 角色，或群里十分钟（网关参数 `hush_s`）没有任何消息时解锁；解锁时的那条消息照常处理。筛选尚未得出结论时又收到 @ 角色的消息，则本次不加锁。
  - 仅批评角色某句话、开玩笑地调侃角色，筛选不视为不希望角色发言。
- **代掷骰子**（`engine/dice.py`）适用于连接器标记了骰子指令和结果、由角色账号代掷的场景。设置 `group.dice: true` 后，角色把结果视为自己替对方掷出的点数。只有有人就结果对角色说话时，筛选才放行。默认关闭，骰子消息只作为自动消息保留在上下文中。`rhine prompt <id> --dice` 可预览启用时的提示词。
- **撤回**：
  - 连接器在撤回的系统消息中携带被撤回消息的 id（见 [protocol.md](protocol.md)）。
  - 原消息保留在历史中不变，因此缓存不受影响；其后追加一条 `kind="recall"` 的提示，引用原消息的开头。
  - 通用规则允许角色提及撤回，但不复述原文：打错字可以直接指出；不友善的话或隐私则含糊带过。
  - 摘要读取不到被撤回的消息，也读取不到提示中的引用。
  - 网关中的滚动摘要等消息超过撤回时限后才读取（连接器在 hello 的 `limits.recall_window_s` 中声明，默认 120 秒）。
  - 角色账号自己撤回的消息（角色的发言、骰子的结果）直接删除，视为从未发送。
- **沉默**：角色可以选择不回复，整条回复只写 `<no_reply/>`。引擎不保存也不发送，这批消息视为角色已读。
- **生成**：回复在开始生成时即在会话中占位，因此生成期间到达的消息排在其后，稍后再回答。被拒绝、出错或沉默时删除该占位；进程在生成中途退出留下的空占位，在网关启动时删除。使用读取原文的工具时，调用工具之前写出的文字不算作回复，只发送最终回答；记笔记和查资料的工具在回复之后调用，回复照常发送。
- **查资料**：角色拥有两个工具，将查询交给专门的 agent 执行，查询完成后角色再回答。
  - `agent_history` 翻阅当前会话以前的记录，可查找原话、厘清时间顺序或总结讨论经过。
    - 角色用自己的话描述要查找的内容（`query`），并附上已知的范围，例如发言者、时间、需要原话还是经过。以约定或事件指代时间时，agent 回到记录中确定范围。
    - `query` 也可以留空：agent 阅读记录的最后几十条，判断群里在聊什么、角色需要什么，再找出相关的时间段。
    - 结果先给出结论，再附几行原文摘录（带编号、时间和发言者），使角色能看到原话。
  - `agent_search` 查询外部资料。配置了本地资料时，相关问题优先查阅本地文件，资料未覆盖或不可用时可以上网查找出处。
  - 两个工具与记笔记一样在回复之后调用：角色先告知对方（「我翻翻」），这句话立即发出；工具只启动查询，立即返回。
  - agent 查询完成后，结果作为一条仅角色可见的消息（`kind="lookup"`，`what` 为查找的内容）加入会话。该消息要求回复，不经过筛选，但受发言锁约束。角色随后回答，并能看到这期间他人的发言。
  - 查询失败（出错、超时）时同样返回一条「这次没查成：……」，角色可以如实告知。结果超过 6000 字时截断。同一个群的同一个工具同一时间只执行一项查询。
  - agent 是本机已登录的命令行 agent（`engine/harness.py`），以无头模式运行，使用订阅额度，不需要 API key。两个工具分别配置使用 Claude Code、Codex 或 Antigravity（`lookup.history`、`lookup.search`）。使用 Claude Code 时，启动前移除 `ANTHROPIC_*` 环境变量。
    - 不读取账号自身的设置，不保存会话。
    - 每个群的每个工具有独立的工作目录（`data/agent/chats/<群的哈希>/history|search/`），其中的指令文件（Claude Code 读取 `CLAUDE.md`，其余两个读取 `AGENTS.md`）说明 agent 正在为角色扮演模型查找资料，以及结果的格式。下文的 `CLAUDE.md` 即指该文件。
    - 翻阅记录时，该群的全部记录导出为工作目录中的 `history.txt`；已撤回的消息、系统提示、系统指令和以往的查询结果不导出。agent 看不到其他群的记录。
    - **索引**：翻阅记录的目录中有一份由 agent 自行维护的 `index.md`，查询结束后保留，供下次使用。每行对应一段时间：日期、编号范围、一句话概括该段内容。索引只用于定位：`CLAUDE.md` 要求每次都回到 `history.txt` 阅读原文、以原文为准，只记录读过原文的内容，发现错误即修正。
      - 上限 3000 字（`INDEX_CHARS`），在 `CLAUDE.md` 中写明；查询结束后超出上限时，系统保留开头部分，在上限以内的最后一个换行处截断。
      - 这是 agent 唯一能写入的文件。Claude Code 只在此时获得 `Edit`/`Write`，权限规则使用绝对路径（`Edit(//…/history/index.md)`）；不能使用 `Edit(./index.md)`，否则子目录中的同名文件也会被放行。Codex 的沙箱无法只放行单个文件，翻阅记录时整个工作目录均可写入。
    - **更早的记录**：插件（`plugins.earlier_history`）可以补充系统开始记录之前的部分。插件提供的行排在 `history.txt` 开头，使用其自己的编号方式，并在指令文件中附一句说明，告知 agent 如何阅读。
    - 翻阅记录时只能读写该工作目录、不能上网；查资料时可以上网、读取配置的资料目录，不能写文件。Git 仓库由引擎更新。各 agent 对这些限制的执行程度不同，见[配置](configuration.md#查资料的-agentlookup)。
    - 安全约束只有一条，写在 `CLAUDE.md` 中，较为宽松：不协助实际的恶意行为（例如编写 DDoS 攻击脚本），了解性的查询照常进行（例如「DDoS 是什么」），agent 平时拒绝的事同样拒绝。
    - 不限制花费，推理档位为 `medium`，查询完成后自行结束。卡住的进程在 `timeout_s`（默认 900 秒）后终止；同时最多运行 `concurrency`（默认 2）个。
  - 可选的 `lookup.reference` 指定资料范围（`description`）、目录（`path`）和格式（`format`）。相对路径以配置文件所在目录为基准。只应指定可供角色检索的资料目录。
    - `text` 直接读取目录中的文本文件。将资料放入该目录即可使用。
    - `git_html` 读取部署者预先克隆的 HTML 仓库。搜索时先尝试快进更新，更新失败时使用已有版本。引擎把变化的 UTF-8 或 GB18030 页面转成 UTF-8 文本，按来源分别缓存在查找工作目录下的 `reference-text/`。
  - 只有写入 `lookup` 的工具（`history`、`search`，各自指定 `harness`，可选 `model`、`effort`、`command`）才对角色可用；对应程序未安装时同样不可用。另可配置 `timeout_s`、`concurrency` 和工作目录 `dir`。命令行聊天等待查询结果返回后再继续回答。
- **图片**：缩放后按内容哈希存放在 `data/media/`，由 `vision` 任务生成一句描述。只有当前回复轮次中、最近 8 条消息内的图片（最多 4 张，`media.live_images`）以原图发给角色。同一文件重复出现时只在最后一次附图，其余位置保留描述。一张图由原图改为描述后，从该位置往后的历史缓存失效，因此只附最近几条消息的原图：角色在群里长时间不发言、图片陆续到达时，需要重写的只是最后一小段。
  - 连接器无法取得原图、只发送缩略图时（`thumbnail: true`），附件记录这一点，记录中的标签带 `thumbnail="true"`，生成描述时也注明为缩略图。连接器之后补发原图（`media_update`）时，替换为原图并重新生成描述。
- **网关**：
  - 同一会话的事件按顺序处理。启用筛选的群中，消息到达即交给筛选，等待时间由筛选决定（见上）；筛选期间有新消息到达时，本次结论作废，由新消息所在的一轮一并判断。私聊（以及未配置筛选的群中必定回复的消息）在最后一条消息之后安静 `debounce`（默认 2.5 秒）才回应，连续发送的多条消息只回复一次。
  - 重写：回复已生成但尚未发出时，只要群里有新消息（任何人，机器人除外）或收到系统指令，该回复即作废、不发送，连同新消息重新生成，模拟真人发送前查看新消息的行为；否则两人先后询问同一件事时，角色会连发两条。最多连续重写 `max_rewrites`（默认 2）次，之后照常发出。作废之前已交给角色的消息仍需回复，即使新消息本身无需回应。
  - 限流：同一会话中，角色两条消息的间隔不少于输入后一条所需的时间，最多 5 秒；不同会话互不等待，也没有全局上限。打字速度按每分钟 100 个英文单词（约 500 次按键）计算，一个汉字计 3 次按键，不计思考时间。
  - 连接器离线时，待回复的消息保留到重连后处理。网关重启时清理尚未开始发送的草稿。开始发送后，网关保留动作编号，重启后仍能认领连接器的回报。明确发送失败时删除回复；结果未知时保留回复，避免重复发送。连接器声明了 `action_dedupe` 时，重启后用原动作编号补问结果。存储失败的事件不回复 ack，等待连接器重发。
  - 单条消息超过连接器的上限（hello 的 `limits.max_text_chars`，默认 2000 字）时，在上限以内的最后一个句末切分，分多条发送，每条单独保存。
  - 过期的消息（`stale_s`，默认 120 秒）不再回复。

- **分条发送**：回复中的空行表示另起一条消息，最多三条（多出的部分并入第三条）。提示词要求角色只在回复长度适中且包含不止一层意思时才分条，分出的每条只是一两句短话；很短的回复、一句话能说清的内容，以及解释规则或道理的内容都只发一条。网关同样把关：各段合计超过 90 字时合并为一条发送（各段之间换行）。只有超过 2000 字的回复才会分成多条长消息。网关逐条发送：前一条确认发出后，等待输入下一条所需的时间（见限流），再检查期间是否有人插话。
  - 有人插话（判断方式与重写相同）时停止发送，剩余部分附在下一次请求的末尾（`<unsent>`），连同插话一并重新回答，角色可以原样发送、修改后发送或不发送；这批消息视为尚未回复。与重写共用 `max_rewrites`，超过后照常发完。
  - 每条单独保存，带各自的 `platform_id`；后续几条不占用限流间隔。前一条 30 秒内未确认发出时，剩余部分不再发送。

## 8. 对外协议

服务端入口是 `rhine-gateway`，一个服务端可承载多个角色，连接器用 `bind` 指定每个会话的角色。运行和部署见[接入聊天软件](gateway.md)，消息格式见[连接器协议](protocol.md)。连接器在 hello 中声明平台的限制（`limits`），网关据此切分长消息，并决定摘要等待多久再读取。

快照工具 `deploy/export_snapshot.py` 用于私下调试。它替换参与者标识和已知昵称，但数据库、引文、消息编号和日志仍可能暴露身份。导出目标应为 `data/` 或 `snapshots/` 下的新目录，并按聊天记录的标准保管。

## 9. 调试与评测

- `rhine chat` 和 `rhine web` 中可以查看完整 prompt、上下文构成、记忆和用量，修改角色包后 `/reload` 立即生效（见[聊天](chat.md)）。
- **日志**（`data/logs/`，命令行和网关均会写入）：
  - `usage.jsonl`：每次 API 调用一行，记录时间、角色、任务（roleplay、reply_judge、vision、summary 等）、会话、模型、结束原因、四类 token（缓存写入中按一小时写入的部分另记为 `cache_write_1h`）和估算费用。每次调用记录耗时 `ms`；回复另记读取长消息的次数 `tool_calls`、记笔记的次数 `notes`、查资料的次数 `lookups`。查资料的 agent 每次一行（`lookup:history`、`lookup:search`）：使用订阅额度，`cost` 记为 0，按 API 价格计算的费用另记为 `api_cost`，并记录轮数 `turns`。供应商控制台只提供总数，按调用分析费用和耗时依赖此日志。
  - `<角色>-thinking.jsonl`：启用 `log_thinking` 时，记录每次回复的思考和原文。
- 聊天文字的长度、标点、分条以及示例的写法见[写角色包](characters.md#回复的写法)。
- 评测场景位于角色包的 `evals/` 下，`rhine eval` 在临时数据目录中逐个运行（`evals.py`），群聊场景同样经过筛选。格式见[写角色包](characters.md#evals评测场景)。

## 10. 本机对话

`rhine chat`（`chat_repl.py`）和 `rhine web`（`web/`）都建在 `local.LocalChat` 上，用法见[聊天](chat.md)。`LocalChat` 的操作（说话、引用、撤回、拍一拍、系统指令、重说）产生事件（`Judged`、`Speaking`、`Streamed`、`Looking`、`Said`、`Failed`），界面只负责显示：终端逐条打印，网页通过 WebSocket 推送到页面。会话 ID 以 `cli:` 开头。

- 引用和撤回依赖消息的 `platform_id`：本机会话中每条消息发出时生成一个，所有角色的副本使用同一个值，因此引用能定位原文，撤回能定位目标消息。
- 拍一拍、邀请入群和移出群聊记录为系统发送者（`system`）的一行文字，与连接器发来的系统消息相同。
- 网页服务和页面文件使用同一个端口：页面地址带一次性生成的 token，WebSocket 和图片请求都需携带该 token；Host 不符的请求（DNS 重绑定）以及其他网站的页面发起的连接均被拒绝。
- 页面位于 `web/static/`，为无需构建的原生 JS 和 CSS，服务端只提供 `STATIC` 中列出的文件。`tokens.css` 定义三套主题（浅色、石墨、墨黑）的颜色、圆角、阴影和动效曲线，`base.css` 包含按钮、选项、开关、菜单、提示等通用控件，`app.css` 负责布局；`app.js` 用 `h()` 构建元素，文字一律作为文本插入，不拼接 HTML。
- 终端的颜色定义在 `colors.py`，与 `tokens.css` 使用同一组配色：长春花蓝强调色，每个发言者一种色相（第一个角色使用强调色）。终端输出使用 `err`、`warn`、`ok`、`accent` 等语义名称，不直接写颜色值；`cli.py` 将 `rhine --help` 的配色设为同一组。

`rhine chat` 的会话：

- **由人数决定方式**：单人和多人对话使用同一套机制，单人对话即只有两名参与者的多人对话。只有一个用户和一个角色时，每条消息都交给角色；对话中有更多参与者（`/as` 切换的用户发过言，或用 `/invite` 邀请了角色）时，每个角色按群聊方式自行判断是否接话。
- **身份与会话分离**：`/as` 只切换发言者，不切换会话。
- **新建和恢复**：`/clear` 新建会话，旧会话原样保留；`/resume` 列出以前的会话（按对话成员标注），选择一个继续；重新启动时进入最近的会话。

多角色对话（`/invite <角色ID>`、`/kick <角色ID>`）：

- **各存一份**：被邀请的角色将该会话保存在自己的数据库中，ID 为 `<会话>@<最初的角色>`，与该角色自身的会话分开。角色只能看到加入之后的消息。
- **互相可见**：每条消息交给所有角色，角色的回复也作为一名群成员的发言交给其他角色。每条用户消息之后，角色之间最多接力 3 次。
- **保持一致**：同一条消息在每一份副本中的时间和内容都相同，`/undo`、`/retry`、`/rewind` 据此同步删除。
- **记录成员**：会话中邀请了哪些角色记录在最初的角色处，重新进入该会话时这些角色一并恢复。

持久化实例（`<角色>:<标签>`，例如 `sample:cafe`）：

- **定义**：同一角色包的实例，拥有独立的数据库（`data/instances/<角色>/<标签>.db`），因此有独立的会话和笔记。笔记在其参与的所有会话之间共享：在一个会话中记录的内容，在另一个会话中仍然可用。不带标签的角色不变，每个会话的笔记相互独立。
- **创建**：聊天中使用 `/instance <角色>:<标签>`，或在命令行中使用 `rhine new <角色>:<标签>`。`/instance` 不带参数时列出所有实例。
- **使用**：`/invite <角色>:<标签>` 将实例邀请进当前对话，或用 `rhine chat <角色>:<标签>` 单独对话。`/kick`、`/memory`、`/forget` 只需写角色 ID，因为一个对话中同一角色只能有一个。
